The `AnsiCode` interface is Clique's primary extension point. Anything that returns a valid ANSI escape sequence can be registered as a named style and used in markup — custom 256-color codes, programmatically generated gradients, values read from a config file at startup. If it speaks ANSI, the parser will use it.

<Note>
  The examples on this page use `Clique.registerStyle()` and `Clique.registerStyles()` for simplicity. These write into a shared global registry visible to every parser in your application. For styles scoped to a specific feature or module, prefer building a [StyleContext](/themes/style-context) and attaching it to just the parsers that need it. The `AnsiCode` implementations shown here work identically in both approaches.
</Note>

## The AnsiCode Interface

`AnsiCode` lives in `clique-spi`. The entire interface is one method:

```java
public interface AnsiCode {
    String ansiSequence(); // return your ANSI escape sequence here
}
```

If your class returns an ANSI escape string from `ansiSequence()`, the parser will use it. You can plug in anything: RGB colors, 256-color codes, composite styles, values loaded from a config file.

<Tip>
  Compute your escape sequence once in the constructor and return the stored value from `ansiSequence()`. There is no need to recompute on every call.
</Tip>

## Custom Colors

Clique ships with `Clique.rgb()` for 24-bit color. For lower-level needs — such as 256-color support for older terminals — implement `AnsiCode` directly:

```java
public class Color256 implements AnsiCode {
    private final String code;

    public Color256(int index, boolean background) {
        if (index < 0 || index > 255) throw new IllegalArgumentException("Color index must be 0-255");
        this.code = "\u001B[%d;5;%dm".formatted(background ? 48 : 38, index);
    }

    @Override
    public String ansiSequence() { return code; }
}

Clique.registerStyle("orange", new Color256(214, false));
Clique.parser().print("[orange]Look ma, 256 colors[/]");
```

If `orange` is only used by one part of your application, scope it with `StyleContext` so other parsers don't pick it up:

```java
StyleContext ctx = StyleContext.builder()
    .add("orange", new Color256(214, false))
    .build();

ParserConfiguration config = ParserConfiguration.builder()
    .styleContext(ctx)
    .build();

Clique.parser(config).print("[orange]Look ma, 256 colors[/]");
```

## Composing Styles

Multiple `AnsiCode` instances can be chained into a single reusable style. This is useful for semantic aliases that carry real meaning in your application:

```java
public class CompositeStyle implements AnsiCode {
    private final String code;

    public CompositeStyle(AnsiCode... codes) {
        var sb = new StringBuilder();
        for (AnsiCode c : codes) sb.append(c.ansiSequence());
        this.code = sb.toString();
    }

    @Override
    public String ansiSequence() { return code; }
}

// Semantic styles that actually mean something
Clique.registerStyle("error", new CompositeStyle(ColorCode.BRIGHT_RED, StyleCode.BOLD));
Clique.registerStyle("warn",  new CompositeStyle(ColorCode.YELLOW, StyleCode.ITALIC));
Clique.registerStyle("ok",    new CompositeStyle(ColorCode.BRIGHT_GREEN, StyleCode.BOLD));

Clique.parser().print("[error]Build failed[/]");
Clique.parser().print("[ok]All tests passed[/]");
```

`StyleContext`'s builder has composition built in, so you often don't need a custom `CompositeStyle` class at all. Passing multiple `AnsiCode` values to `add()` combines them for you:

```java
StyleContext ctx = StyleContext.builder()
    .add("error", ColorCode.BRIGHT_RED, StyleCode.BOLD)
    .add("warn",  ColorCode.YELLOW, StyleCode.ITALIC)
    .add("ok",    ColorCode.BRIGHT_GREEN, StyleCode.BOLD)
    .build();

ParserConfiguration config = ParserConfiguration.builder()
    .styleContext(ctx)
    .build();

Clique.parser(config).print("[error]Build failed[/]");
Clique.parser(config).print("[ok]All tests passed[/]");
```

## Dynamic Style Generation

Since styles are just `AnsiCode` instances, you can generate them programmatically. Here's a gradient registered as a set of indexed tags:

```java
public static void registerGradient(String name, int[] from, int[] to, int steps) {
    Map<String, AnsiCode> gradient = new HashMap<>();

    for (int i = 0; i < steps; i++) {
        double t = (double) i / (steps - 1);
        int r = (int) (from[0] + t * (to[0] - from[0]));
        int g = (int) (from[1] + t * (to[1] - from[1]));
        int b = (int) (from[2] + t * (to[2] - from[2]));
        gradient.put(name + "-" + i, Clique.rgb(r, g, b));
    }

    Clique.registerStyles(gradient);
}

// Coral to purple, 5 steps
registerGradient("sunset", new int[]{255, 94, 77}, new int[]{138, 35, 135}, 5);

Clique.parser().print("[sunset-0]█[/][sunset-1]█[/][sunset-2]█[/][sunset-3]█[/][sunset-4]█[/]");
```

Generated gradients are a good candidate for scoping. The indexed names (`sunset-0`, `sunset-1`, ...) are easy to collide with something registered globally elsewhere. Building the map into a `StyleContext` keeps it contained:

```java
public static StyleContext gradientContext(String name, int[] from, int[] to, int steps) {
    Map<String, AnsiCode> gradient = new HashMap<>();

    for (int i = 0; i < steps; i++) {
        double t = (double) i / (steps - 1);
        int r = (int) (from[0] + t * (to[0] - from[0]));
        int g = (int) (from[1] + t * (to[1] - from[1]));
        int b = (int) (from[2] + t * (to[2] - from[2]));
        gradient.put(name + "-" + i, Clique.rgb(r, g, b));
    }

    return StyleContext.from(gradient);
}

StyleContext ctx = gradientContext("sunset", new int[]{255, 94, 77}, new int[]{138, 35, 135}, 5);

ParserConfiguration config = ParserConfiguration.builder()
    .styleContext(ctx)
    .build();

Clique.parser(config).print("[sunset-0]█[/][sunset-1]█[/][sunset-2]█[/][sunset-3]█[/][sunset-4]█[/]");
```

## Loading Styles from a Config File

If you want your styles to live outside the codebase — in a `colors.json` or a `.theme` file — load and register them at startup:

```java
// colors.json
// {
//   "brand":   { "r": 66,  "g": 135, "b": 245 },
//   "accent":  { "r": 156, "g": 39,  "b": 176 }
// }

JsonObject styles = JsonParser.parseString(Files.readString(Path.of("colors.json"))).getAsJsonObject();
Map<String, AnsiCode> loaded = new HashMap<>();

for (var entry : styles.entrySet()) {
    JsonObject c = entry.getValue().getAsJsonObject();
    loaded.put(entry.getKey(), Clique.rgb(
        c.get("r").getAsInt(),
        c.get("g").getAsInt(),
        c.get("b").getAsInt()
    ));
}

Clique.registerStyles(loaded);
Clique.parser().print("[brand]Styled from config[/]");
```

If `brand` and `accent` really are constants shared across your whole application, this is a reasonable use of the global registry. If they belong to one specific part of the app, build a `StyleContext` from the same map instead:

```java
StyleContext ctx = StyleContext.from(loaded);

ParserConfiguration config = ParserConfiguration.builder()
    .styleContext(ctx)
    .build();

Clique.parser(config).print("[brand]Styled from config[/]");
```

## Keeping Global Registration Clean

If your application registers many custom styles globally, centralizing them in a single class with a guard prevents accidental double-registration:

```java
public class AppStyles {
    private static boolean registered = false;

    public static synchronized void register() {
        if (registered) return;

        Clique.registerStyles(Map.of(
            "error", new CompositeStyle(ColorCode.BRIGHT_RED, StyleCode.BOLD),
            "warn",  new CompositeStyle(ColorCode.YELLOW, StyleCode.ITALIC),
            "ok",    new CompositeStyle(ColorCode.BRIGHT_GREEN, StyleCode.BOLD)
        ));

        registered = true;
    }
}

// At startup
AppStyles.register();
```

The guard exists because `Clique.registerStyles()` writes into shared global state. Calling it more than once, or from more than one place, risks re-registering or silently overwriting styles.

If your styles don't need to be global, `StyleContext` sidesteps the problem entirely — it's a value you construct and pass around like any other object, with no shared state and no guard needed:

```java
public class AppStyles {
    public static final StyleContext CONTEXT = StyleContext.builder()
        .add("error", ColorCode.BRIGHT_RED, StyleCode.BOLD)
        .add("warn",  ColorCode.YELLOW, StyleCode.ITALIC)
        .add("ok",    ColorCode.BRIGHT_GREEN, StyleCode.BOLD)
        .build();
}

// Wherever a parser needs these styles
ParserConfiguration config = ParserConfiguration.builder()
    .styleContext(AppStyles.CONTEXT)
    .build();

Clique.parser(config).print("[error]Build failed[/]");
```

`AppStyles.CONTEXT` is immutable once built, so there's nothing to guard. It's constructed exactly once as a static field, and every parser that uses it sees the same fixed set of styles.

## API Reference

### Color Factories

| Method | Description |
|---|---|
| `Clique.rgb(int r, int g, int b)` | Creates a 24-bit RGB foreground color |
| `Clique.rgb(int r, int g, int b, boolean background)` | Creates a 24-bit RGB color, foreground or background |
| `Clique.hex(String hexCode)` | Creates a foreground color from a `#RRGGBB` hex string |
| `Clique.hex(String hexCode, boolean background)` | Creates a color from a `#RRGGBB` hex string, foreground or background |

### Composition

| Method | Description |
|---|---|
| `Clique.compose(AnsiCode... ansiCodes)` | Combines multiple `AnsiCode` instances into a single composite code applied left to right |
| `Clique.compose(Collection<AnsiCode> ansiCodes)` | Combines a collection of `AnsiCode` instances into a single composite code in iteration order |

### Registration

| Method | Description |
|---|---|
| `Clique.registerStyle(String name, AnsiCode code)` | Registers a single named style in the global registry |
| `Clique.registerStyles(Map<String, AnsiCode> codes)` | Registers multiple named styles from a map |
